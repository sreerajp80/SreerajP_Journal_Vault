# A1.2 — Inline images in the editor body

**Status:** completed

Implements idea **A1.2** from [`docs/enhancement_ideas.md`](../docs/enhancement_ideas.md).

## What the issue is

Today an image can only be added as an attachment. It shows up as a file name in the attachment
tray under the editor, never inside the writing. A diary where a photo is a row in a list, and not
part of the page, reads like a form.

Everything needed is already built:

- `AesGcmAttachmentCryptoStorage.encryptAndStore` / `decryptToTempFile` handle any bytes.
- `AttachmentTempFileManager` owns the plaintext temp file and sweeps it when the app backgrounds.
- `AttachmentImportService.importToEntry` already encrypts and writes the `Attachments` row, with
  rollback when the database write fails.
- `table_embed.dart` and `callout_embed.dart` show exactly how a custom Quill embed is written in
  this app.

What is missing is a Quill embed that points at an attachment row, decrypts it to a temp file and
renders it — plus a toolbar button to make one, and export support so the picture is not lost when
the entry leaves the app.

Two smaller problems found while reading the code, both in scope because this change touches them:

1. `_RevisionPreviewScreen` in `version_history_screen.dart` renders a revision with
   `QuillEditor.basic` and **no embed builders**. Tables and callouts already fail to render there;
   an inline image would too. Fixed by registering the builders in the preview.
2. `_handleAddAttachment` in the editor calls `picker.pickAttachment()` and **throws the result
   away** — a picked attachment is never imported. That is an existing bug, not this idea, so it is
   *not* fixed here; it is noted at the end of this plan as follow-up work.

## Design decisions

**The image is a normal attachment row.** The embed stores only the attachment id. So an inline
image is encrypted, backed up, synced, migrated between app-private and SD card, and exported by
every path that already exists. No new table, no migration.

**A new embed type key, `vault_image`.** Not `image` — Quill's own built-in image embed uses that
key and expects a URL or base64 in the delta. Ours must never hold image bytes in the document
JSON, because the document JSON is stored unencrypted in the `Entries` table.

Embed data (a JSON string, same shape convention as callout/table):

```json
{"attachmentId": 12, "fileName": "beach.jpg", "widthFactor": 1.0}
```

`widthFactor` is 1.0 / 0.66 / 0.4 — full, medium, small — chosen from a menu on the image.

**A locked attachment stays locked inline.** If the attachment carries a lock, the embed renders a
grey "Locked image — tap to unlock" box, and tapping runs the same `BiometricAuthenticator` prompt
the attachment tray uses. Otherwise an inline image would be a way around a lock the user set
deliberately. This follows the Sensitive Data profile.

**Decryption is cached per screen.** A new `InlineImageStore` holds one `AttachmentTempFileHandle`
per attachment id for the life of the editor screen, so scrolling does not re-decrypt. It releases
every handle on dispose, so the plaintext copies go away when the screen closes.

**The store takes callbacks, not a database.** It is built in the screen from `ref`, so it stays a
plain Dart class that can be tested with fakes and no drift.

## Files to be changed

### Phase 1 — the embed in the editor

| File | Change |
|---|---|
| `lib/features/entries/presentation/editor/image_embed.dart` | **New.** `VaultImageEmbed` (type `vault_image`, `attachmentId` / `fileName` / `widthFactor`) and `VaultImageEmbedBuilder`. Renders the picture, a size menu, a delete button; tap opens it full screen. Shows a locked box, an "image unavailable" box, or a spinner as the state requires. |
| `lib/features/entries/presentation/editor/inline_image_store.dart` | **New.** Caches `attachmentId → AttachmentTempFileHandle`, tracks which locked images have been unlocked this session, releases everything on `dispose()`. Takes `lookUpAttachment`, `isLocked`, `decrypt` and `authenticate` callbacks. |
| `lib/features/attachments/services/attachment_open_service.dart` | `AttachmentImportService.importToEntry` returns the new attachment id (`Future<void>` → `Future<int>`). Same body, plus the id. Existing callers ignore the result and keep working. |
| `lib/features/entries/presentation/editor/editor_toolbar.dart` | New `onInsertImage` callback and an `Icons.image_outlined` button next to the table and callout buttons. |
| `lib/features/entries/presentation/entry_editor_screen.dart` | Pull the attachment-permission gate out of `_handleAddAttachment` into `_ensureAttachmentPermission()` and reuse it. Add `_insertImage()`: permission → pick → reject anything that is not `image/*` with a SnackBar → import through `AttachmentImportService` → insert the embed plus a trailing newline (same trick tables and callouts use so the cursor is not trapped) → refresh the attachment tray. Build the `InlineImageStore`, add `VaultImageEmbedBuilder` to `_embedBuilders`, dispose the store. |
| `lib/features/entries/presentation/version_history_screen.dart` | Register table, callout and image builders on the revision preview so embeds render there instead of failing. |

### Phase 2 — export

Without this, an exported entry shows `[vault_image block — not exportable as text]` where the
picture was. The bytes are not lost (the image is an attachment and is written into the zip), but
the page is wrong.

| File | Change |
|---|---|
| `lib/features/export/services/delta_document.dart` | New `ImageBlock(attachmentId, fileName)`; parse `vault_image` into it, falling back to `UnknownEmbedBlock` on bad data as the other embeds do. |
| `lib/features/export/services/delta_to_plain_text.dart` | `[Image: beach.jpg]` on its own line. |
| `lib/features/export/services/delta_to_markdown.dart` | `![beach.jpg](attachments/12_beach.jpg)` when attachments are included — the path matches the zip layout `ExportService` already writes — otherwise a plain `*[Image: beach.jpg]*` line. |
| `lib/features/export/services/delta_to_html.dart` | Render `<figure class="inline-image"><img src="..."></figure>` from an optional `Map<int, String>` of attachment id → `data:` URI. An id with no entry in the map renders the same greyed placeholder line an unknown embed gets. |
| `lib/features/export/services/export_html_builder.dart` | Accept the id → data-URI map and pass it down. New CSS for `figure.inline-image` (max width, page-break avoidance for print). |
| `lib/features/export/services/export_service.dart` | Before rendering HTML/PDF, walk every `ImageBlock`, decrypt the matching attachment and build the data URI. Locked images are never decoded — they are skipped and reported through `ExportResult.skipped`, the same rule `_collectAttachmentFiles` follows. Unreadable ones are reported too. Images are resolved even when "include attachments" is off, because an inline image is part of the page, not an extra file. |
| `lib/features/export/export_strings.dart` | Two strings: an inline-image placeholder label, and the "locked image left out" omission line. |
| `lib/features/export/services/export_collector.dart` | Collect attachment refs whenever the document holds an `ImageBlock`, even when `includeMetadata`/`includeAttachments` are off, so `ExportService` can find the row to decrypt. |

## What is deliberately not in this plan

- **Drag-to-resize and image cropping.** The size menu covers the need; a resize handle inside a
  Quill embed is a much bigger piece of work (idea A1.3 territory).
- **Pasting or dropping an image into the editor.** Insert is through the toolbar button only.
- **Fixing `_handleAddAttachment` dropping its picked file.** A real bug, but a separate one — it
  predates this change and deserves its own plan so its fix is logged on its own.

## Order of work

1. Phase 1, ending with the editor showing a picture in the body.
2. Phase 1 tests.
3. Phase 2, export.
4. Phase 2 tests.
5. `dart format`, `flutter analyze`, `flutter test`.
