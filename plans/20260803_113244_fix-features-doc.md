# Fix docs/features.md — correct stale claims and fill gaps

**Status:** completed

## Files to be changed

- `docs/features.md` (only file changed)

## What the issue is

`docs/features.md` lists the app's features. A recent "last-mile integration pass" (see
`docs/architecture.md` section 21) deleted several files the doc's descriptions were built
around, and disabled one whole feature area at the flag level. The doc was not updated to
match. I checked the claims below directly against the current code, not just the earlier
background-agent report.

Confirmed problems:

1. **Permissions Center is described wrong.** `docs/features.md` line 150 says the Permissions
   Management Center covers "Storage, Microphone, Biometrics, Notifications". The actual code
   (`lib/features/permissions/domain/app_permission_models.dart` line 1) only defines
   `AppPermissionId { attachmentImport, documentPicker }` — both storage-related. There is no
   microphone, biometrics, or notifications permission item anywhere in this screen.

2. **Sync engine is presented as a live feature, but it is switched off and cannot function.**
   `lib/core/config/app_flavor_config.dart` line 62, `enableSyncUi => false`, with a comment
   explaining `SyncProtocol` has no concrete transport — nothing can ever push or pull. Section 7
   of `docs/features.md` describes vector clock sync, E2E encryption, and a conflict UI as
   working features with no caveat that the UI is hidden and the feature is non-functional today.

3. **"Production-grade" claim in the opening paragraph is overstated.** `docs/architecture.md`
   section 21 "Still open — release-blocking" says the release keystore does not exist yet, so
   release builds currently fall back to the debug key. The doc should not imply the app is
   release-ready without noting this.

4. **Home tab / Search tab file references are stale.** `home_screen.dart` and
   `search_screen.dart` were deleted; both tabs were folded into `_HomeTab` / `_SearchTab` inside
   `lib/app/app.dart`. `docs/features.md` section 8 line 146 already just says "`app.dart`" for
   navigation, so no filename fix is needed there, but nothing in the doc should later be edited
   to reference the deleted screen files.

5. **Several known Sensitive-Data gaps are not disclosed**, per `docs/architecture.md` section 21
   "Still open — Sensitive Data":
   - No "Delete all data" action anywhere in the app.
   - The SQLite database and its FTS index are **not** encrypted at rest — only attachments are.
     `docs/features.md`'s opening paragraph and section 4 could be read as implying the whole
     data layer is encrypted; only attachments and Keystore-held secrets are.
   - The attachment crypto format has no version byte yet.

6. **Attachment viewer host screen is missing from the doc.** Section 3 names the three viewer
   bodies (`pdf_attachment_view.dart`, `audio_attachment_view.dart`,
   `archive_attachment_view.dart`) but not the shared host/shell screen that owns the decrypted
   temp file and routes to them: `attachment_viewer_screen.dart`.

## The plan for the fix

Edit `docs/features.md` only, in place, no new files:

1. **Opening paragraph (App Description):** add one caveat sentence noting the app is under
   active hardening — release builds are not yet signed with a release key, and only attachments
   (not the SQLite database or FTS index) are encrypted at rest. Keep the sentence short, per the
   simple-English rule.

2. **Section 1 (Security, Privacy & Data Protection):** add one bullet listing the disclosed
   gaps: no "Delete all data" action yet, database/FTS index stored unencrypted (attachments are
   still AES-256-GCM encrypted), attachment crypto format has no version byte yet. Point to
   `docs/architecture.md` section 21 for detail instead of duplicating it.

3. **Section 3 (Media Attachments & Secure Viewers):** add a bullet for the shared host screen
   `attachment_viewer_screen.dart` that owns the decrypted temp file and dispatches to the PDF /
   audio / archive bodies, and note that plaintext is deleted on dispose for in-app viewing.

4. **Section 7 (Multi-Device Encrypted Sync Engine & Conflict Resolution):** add a leading note
   that this feature is implemented and tested but currently **disabled** behind
   `AppFlavorConfig.enableSyncUi` (`false`) because `SyncProtocol` has no transport yet, so no
   data currently syncs. Keep the rest of the section as-is since the underlying code is real,
   just not reachable from the UI yet.

5. **Section 8, Permissions Management Center bullet (line 150):** correct the permission list
   from "Storage, Microphone, Biometrics, Notifications" to what the code actually exposes today
   — storage-related permissions for attachment import and document picking
   (`attachmentImport`, `documentPicker`).

No other sections need changes — the earlier background audit's other checks (DAOs list,
top-level feature directories, pubspec dependencies) came back accurate against the doc as
written.
