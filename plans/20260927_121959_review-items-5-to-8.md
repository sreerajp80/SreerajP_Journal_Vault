## Item 5 — Re-editing a drawing deletes the old picture too early

### Issue

`_editDrawing` in `lib/features/entries/presentation/entry_editor_actions_3.dart` (lines 163–236)
saves the edited drawing as a **new** attachment and swaps the embed in the text. Then it deletes
the **old** attachment row and file straight away.

But the old embed can come back:

- **Undo** in the editor puts the old embed back. It now points at an attachment that no longer
  exists, so it shows the "missing drawing" placeholder. Redo cannot bring the picture back either.
- **Version history.** Every save, including each autosave, stores the previous content as a
  revision. Restoring a revision from before the re-edit shows the placeholder too.

The same code also breaks the layer rule. It calls `attachmentsDao.getAttachmentById` and
`attachmentsDao.deleteAttachmentById` from a widget, and it skips `EntryDeletionService`. It
swallows every error with `catch (_) {}`.

### Fix

1. **Do not delete at re-edit time.** `_editDrawing` records the old attachment ID in a new
   editor field, `_supersededDrawingIds` (a `Set<int>`), and stops there. Undo and redo work for
   the whole editing session.
2. **Clean up when the editor closes.** In `dispose`, if the set is not empty, call a new method
   `EntryDeletionService.deleteUnreferencedAttachments(entryId, ids)`, without awaiting it. The
   method:
   - reads the entry's **saved** `content_json` from the database, not the on-screen document;
   - finds which of `ids` the saved content still shows, using the existing
     `attachmentEmbedOffsets` logic, moved to a pure helper usable from a service (see below);
   - deletes the rest through the existing `deleteAttachment`, which removes row and file in the
     right order;
   - never throws, and logs only counts.
3. **Move the embed scan out of `presentation/`.** Services must not import widget files.
   `attachmentEmbedOffsets` lives in `presentation/editor/attachment_embed_finder.dart` and
   depends on the embed widget classes. Add a small pure function,
   `attachmentIdsInDelta(List<dynamic> deltaJson) → Set<int>`, in
   `lib/features/entries/domain/`. It reads the two embed keys (`vaultImage`, `drawing`) by their
   string names. `attachment_embed_finder.dart` keeps working as it is.

### Known limit (accepted, unless you decide otherwise)

After the editor closes, the old drawing is gone. Restoring a revision from before the re-edit
still shows the placeholder. This is the same as today for any attachment the user deletes from
the tray. Keeping old drawings for revisions would fill the attachment tray with every past
version of every drawing, because the tray lists all of an entry's attachments.

### Tests

- `test/features/entries/services/entry_deletion_service_test.dart`: with an entry whose saved
  content shows attachment A but not B, `deleteUnreferencedAttachments(entry, {A, B})` deletes
  only B (row and file).
- New `test/features/entries/domain/attachment_ids_in_delta_test.dart`: finds image and drawing
  IDs, and ignores other embeds and plain text.

### Files

- `lib/features/entries/presentation/entry_editor_actions_3.dart`
- `lib/features/entries/presentation/entry_editor_screen.dart` (the new field, and `dispose`)
- `lib/features/entries/services/entry_deletion_service.dart`
- `lib/features/entries/domain/attachment_ids_in_delta.dart` (new)

DAO types or call a DAO. Today 20 widget files call DAOs or `appDatabaseProvider` directly, in
about 90 places. (`lib/app/app.dart` also uses it, but only to override the provider at start-up,

### Fix — general approach

- Each widget reads a **provider** instead. Reads become `FutureProvider` or `StreamProvider`
  (reusing `homeJournalsProvider`, `allTagsProvider`, `allUserTemplatesProvider`,
  `entryTagsProvider`, `allTimeCapsulesProvider` where they fit). Writes go through a **service**
  exposed by a `Provider`.
- Services are small, one per area, in the feature's `services/` folder, and take `AppDatabase` in
  their constructor. They hold no `BuildContext` and no UI strings.
- Where a widget only passes the database into a service constructor, a provider builds that
  service instead.
- **Behaviour must not change.** No new features, no UI changes, no schema change. Existing widget
  tests must pass unchanged. Where one needs a new provider override, that is the only change
  allowed in it.
- Every new service gets unit tests against an in-memory database.

## Item 7 — Sync puts remote table and column names straight into SQL

### Issue

Wi-Fi Sync builds SQL text from names that come from the other phone:

- `lib/features/sync/services/sync_engine_records.dart`: `INSERT INTO $table ($columns) …`
  (line 255), `UPDATE $table SET $setClause …` (line 333), `SELECT * FROM $table …` (line 159).
  `$table` is `remoteRecord.recordTable`, and `$columns` / `$setClause` are the keys of the
  decrypted remote record.
- `lib/features/sync/services/conflict_resolution_service.dart` line 202: the same `UPDATE`, with
  the table name stored earlier from a remote record.

Nothing checks the table name against `SyncEngine.syncableTables`, and nothing checks the columns
against the real table. The other phone must be paired and hold the shared key, so this is not
open to strangers. But a buggy or newer app version on the other phone could write to a table
that is never meant to sync (for example `app_security` or `sync_metadata`), or break the SQL with
an unknown column.

### Fix

1. New file `lib/features/sync/services/sync_schema_guard.dart`, holding a `SyncSchemaGuard`
   built from the `AppDatabase`:
   - `bool isSyncable(String table)`: true only for names in `SyncEngine.syncableTables`.
   - `Map<String, Object?> knownColumns(String table, Map<String, Object?> data)`: returns only
     the keys that are real columns of that table, read from Drift's own table list
     (`db.allTables` → `actualTableName` / `$columns`), not from the remote data. Keys that start
     with `_` (the internal `_attachmentBytesBase64`) are handled by the caller before this, as
     today.
2. `_insertRemoteRecord`, `_updateLocalRecord`, the conflict-creating branch in `pull`, and
   `ConflictResolutionService._applyDataToRecord` check `isSyncable` first. A record for any other
   table is **skipped** (not applied, not stored as a conflict), and one warning with the count of
   skipped records is logged, with no names or data.
3. Column maps pass through `knownColumns` before the SQL is built. Unknown columns are dropped,
   so a newer phone that has an extra column still syncs the columns this phone knows. If nothing
   is left, the record is skipped.
4. Values still go in as bound `?` variables, as they do today.

This slice does **not** fix the attachment path, the Keystore key name, or the missing journal and
entry ID mapping (review items 2 and 3). Those need their own plan.

### Tests

New `test/features/sync/sync_schema_guard_test.dart`:

- `isSyncable` accepts every name in `syncableTables` and rejects `app_security`,
  `sync_metadata`, `sqlite_master`, and a name with SQL in it (for example `entries; DROP TABLE x`).
- `knownColumns` keeps real columns and drops unknown ones and ones with SQL in the name.

Plus one case in `test/features/sync/sync_engine_wifi_test.dart`: a pulled record for a
non-syncable table is skipped, and the rest of the pull still applies.

## Item 8 — Error text in log messages

### Issue

Since 2026-09-19, release builds write `info` and above to logcat. `AppLogger` logs only an
error's **type** in prod when the error is passed as `error:`. But eight log calls put the error
straight into the message text with `$e`, which skips that filter:

| File | Line(s) |
|---|---|
| `lib/features/entries/presentation/ocr_camera_controls.dart` | 225, 329 |
| `lib/features/entries/services/ocr_camera_source_store.dart` | 39, 50 |
| `lib/features/entries/services/ocr_language_store.dart` | 46, 58 |
| `lib/features/entries/services/platform_notification_service.dart` | 32, 43 |

The camera and settings-store errors are unlikely to hold journal content. But a
`PlatformException` from the notification plugin can repeat what was sent to it, which for a time
capsule may be the entry title. That breaks hard rule 3.

There is a second, related point. In the **dev** flavor, `AppLogger._fullErrors` logs the full
error text. CLAUDE.md hard rule 3 says "not even in debug builds", and error text can hold a file
name or path, and attachment names are private.

### Fix

1. In each of the eight calls, change `…failed: $e'` to `…failed', error: e`. The logger then
   applies its prod filter. `$nextMode` (a flash mode enum) stays in the text, because it is not
   user data.
2. **Decision for you — dev full errors:**
   - **Option A (recommended):** log only the error's type in every flavor. Remove `_fullErrors`
     and the `fullErrors` test parameter, and update `test/core/logging/app_logger_test.dart`.
     This matches rule 3 exactly. A developer who needs more detail can debug locally.
   - **Option B:** keep full error text in dev only, and add a line to `docs/security.md` saying
     so, as a documented exception to rule 3.
3. Add a guard test, `test/core/logging/no_raw_error_in_log_message_test.dart`. It scans
   `lib/**/*.dart` for an `AppLogger.<level>(` call whose message text holds `$e`, `${e}`,
   `$error`, `$err`, `$ex`, `$exception`, `.message` or `.toString()`, and fails with the file and
   line. Plain `test`, not `testWidgets`, so real file reads work.

### Files

- The four files in the table above
- `lib/core/logging/app_logger.dart` and `test/core/logging/app_logger_test.dart` (Option A only)
- `docs/security.md` (Option B only)
- `test/core/logging/no_raw_error_in_log_message_test.dart` (new)

## Related finding (not in this plan)

While checking item 5, the editor turned out to have a data-loss bug. `_markDirty`
(`entry_editor_actions.dart` line 280) saves 2.5 seconds after the last keystroke. `dispose`
(`entry_editor_screen.dart` line 229) **cancels** that timer, and nothing saves when the user
leaves the screen. So text typed in the last 2.5 seconds before pressing Back, or before the app
locks, is lost. This needs its own plan, and should be fixed before slice 6b, which moves the
save code.
