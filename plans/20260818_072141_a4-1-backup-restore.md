# A4.1 — Restore from a backup

**Status:** completed

Implements idea **A4.1** in `docs/enhancement_ideas.md` (lines 316–338), the top-priority gap in
that document.

> **Revision 2.** The four sister apps were read directly from source, not from their summaries.
> That changed two things: the attachment problem in §2.4 now has an off-the-shelf answer, so the
> Option A / Option B question I raised is withdrawn; and the error types, the passphrase rule and
> the backup-file list in §2.5 are now copied from real code rather than invented.

---

## 1. The issue

`lib/features/backup/services/backup_service.dart` can **create** an encrypted `.vault` archive
and **verify** that it decrypts and holds a manifest. It cannot read one back. There is no
restore service, no restore screen, and no test.

So today:

- A lost, wiped or replaced phone means every journal entry is gone, no matter how many backups
  were taken. The backup file is just a file nobody can open.
- The backup is also incomplete. `_exportDatabase()` skips **entry moods** and **saved search
  presets**, which are user data the person cannot recreate.
- Attachments are copied into the archive **still encrypted with the device Keystore key**, and
  that key is not in the archive. On a new phone those files are unopenable rubble (§2.4).
- The manifest carries `"version": 1` but no database schema version, so the app cannot tell an
  old archive from a newer one it does not understand.
- There is no way to even *see* which backup files exist. They are written to a private folder
  the user cannot browse.

## 2. What we will build

Read from source in the sibling apps:

| Source | What was actually there | What we take |
|---|---|---|
| `chronotune-smart-clock` `data/BackupManager.kt` | `FORMAT_VERSION = 1` in the JSON root, `enum class ImportMode { MERGE, REPLACE }`, REPLACE clears the tables first, rows re-inserted without their ids. | The mode enum, the version field, and dropping primary keys on import. |
| `sreerajp_todo` `data/backup/backup_service.dart` | Whole database file inside a password-protected ZIP. Import = extract → `PRAGMA user_version` check → `BackupVersionTooNewException` if newer → migrate if older → `PRAGMA integrity_check` → `AtomicSaver.replaceFileAtomically` with a safety copy and rollback. Export checkpoints WAL and closes the database first. Passphrase must be at least 8 characters. | The safety sequence and the exact exception shapes. Not the file swap — see §2.2. |
| `SreerajPContactSphere` `services/backup_service.dart` | `"CSBK"` magic + a format-version byte, PBKDF2 + AES-256-GCM over a framed container that holds the metadata JSON **and the raw photo bytes**, then a full replace. Restore screen sits behind a biometric check. | The container that carries binary assets *as content*, and the gate. This is the answer to §2.4. |
| `SreerajP_Authenticator` `services/export_import_service.dart` | `v3:<salt_b64>:<nonce_b64>:<ciphertext_b64>`, with `v2:` and an older CTR form still decryptable. `ImportResult { accountsAdded, accountsSkipped }`. | Self-describing envelope, reading old formats, and the added/skipped result. |

User-visible result: **Settings → Backup Health → Restore from backup**, which asks for
PIN/biometric, lists the backups the app has already made *and* lets the user pick a file, asks
for the password, shows a **preview** of what is inside, offers **Replace** or **Merge**, offers a
**dry run**, and ends with a result dialog saying what was added and what was skipped.

### 2.1 Format version 2 (old archives stay readable)

`manifest.json` gains three fields, and the format version goes to **2**:

```json
{ "formatVersion": 2, "schemaVersion": 8, "tables": { "entries": 120 } }
```

`version: 1` stays in the file so an older build still recognises it. Reading rules:

- Missing `formatVersion` → treat as version 1 (today's archives). Still restorable.
- `formatVersion` newer than the app supports → `BackupVersionTooNewException`.
- `schemaVersion` greater than `AppDatabase.schemaVersion` → `BackupVersionTooNewException`, with
  a message telling the user to update the app. This is `sreerajp_todo`'s `PRAGMA user_version`
  check; our archive has no database file, so the manifest carries the number instead.
- Older or missing `schemaVersion` → accepted. Our archive stores **JSON rows**, so a column that
  did not exist yet simply takes its default. That is why we need no equivalent of the todo app's
  external-database migration step.

Version 2 also exports `entryMoods` and `searchPresets`, so a v2 archive is a complete copy of
user data. `attachmentTexts` is deliberately **not** exported — it is a derived search index,
rebuilt after a restore.

### 2.2 Why we do not copy the atomic file replace

`sreerajp_todo` swaps the whole SQLite file with `AtomicSaver.replaceFileAtomically`, keeping a
safety copy and rolling back on error. That works because its backup *is* a database file.

Ours is JSON rows, and it must also support merge, which a file swap cannot do. The equivalent
guarantee here is:

- everything applies inside **one Drift transaction** that rolls back on any error, and
- before a REPLACE the app takes an **automatic pre-restore backup** of the current data, logged
  with trigger `pre_restore`, so a bad restore is undoable.

Together these give the same "you cannot end up half-restored" promise. Likewise the todo app's
WAL checkpoint before export does not apply: we export by running queries, not by copying the
file.

### 2.3 The safety sequence

1. **Gate** — PIN if one is set, else a device-credential / biometric prompt
   (`SreerajPContactSphere` §7). If neither exists the screen opens, because there is nothing to
   check against.
2. **Password** — at least 8 characters (`CryptoUtils.validatePassphrase` in the todo app), then
   decrypt. Failure gives "wrong password, or the backup file is damaged" — we cannot tell the two
   apart, and both sister apps say exactly that.
3. **Version check** — as in §2.1.
4. **Structure check** — `manifest.json` and `database.json` present and parseable.
5. **Preview** — per-table counts shown before anything is touched.
6. **Dry run** — pre-selected the first time. Runs the whole plan and reports
   added / skipped / replaced counts **without writing anything**. This is ours; none of the four
   has it, and it is what makes a merge safe to try.
7. **Pre-restore safety backup** — before a REPLACE only.
8. **Apply** — one transaction.
9. **Verify** — `PRAGMA integrity_check`, then rebuild the FTS index
   (`INSERT INTO entries_fts(entries_fts) VALUES('rebuild')`, and the same for
   `attachment_text_fts`).
10. **Log** — a row in `backup_logs` with trigger `restore` and status `success` or `failed`. The
    `trigger` column is free text, so **no schema change and no migration are needed.**

Exceptions copy the todo app's shapes so the family stays consistent:
`BackupVersionTooNewException(backupVersion, appVersion)` and `BackupCorruptedException(details)`
with the detail codes `wrong_passphrase`, `invalid_archive`, `integrity_check_failed`.

### 2.4 Attachments — solved, not a decision any more

I previously asked whether to export the Keystore attachment key. **That question is withdrawn.**
`SreerajPContactSphere` already solves this shape: it packs the **photo bytes themselves** into
the container and encrypts the whole container under the user's passphrase. The device key never
appears in the file.

We do the same:

- **On export (v2):** decrypt each attachment with the Keystore key, write the **plaintext bytes**
  into the archive, file by file. The archive as a whole is already AES-256-GCM under the backup
  password, so nothing is ever written in the clear.
- **On restore:** re-encrypt each file with **this** device's Keystore key, write a fresh nonce,
  and store the new `nonceBase64`, `keyReference` and `encryptedPath` on the row.

Result: attachments restore and open on a brand-new phone, the Keystore key never leaves the
device, and `MainActivity.kt` does not change at all. The trade-off is stated plainly in
`docs/security.md`: the backup password is now the only thing protecting attachment content, so a
weak one is worse than before. The 8-character minimum in step 2 is the floor.

- **Restoring a v1 archive** (anything made before this change) keeps the old behaviour: the
  bytes are copied as-is, and the result dialog warns that those attachments open only if the
  original device key is still present. Old backups are never orphaned — the
  `SreerajP_Authenticator` rule.

### 2.5 Replace vs merge, and the backup list

- **REPLACE** — clear the user-data tables, then insert the archive's rows (chronotune's
  `ImportMode.REPLACE`).
- **MERGE** — insert only rows the app does not already have; the rest count as skipped. Match
  rules: journals by title + createdAt; entries by journal + title + createdAt; tags by name
  (case-insensitive); attachments by entry + file name + createdAt; moods by entry.

In both modes the archive's primary keys are **dropped, not reused**. Each row is inserted without
an id, the new id is captured, and old→new maps for journals, entries, tags and attachments
rewrite the foreign keys in entries, tag links, attachments, backlinks, revisions, voice notes,
moods and sync metadata. This is what stops a merge from overwriting an unrelated existing entry
that happens to share id 7.

The restore screen also lists the app's own backup files with date and size, copying
`listBackups()` and the backup tile from the todo app, so the user can restore without hunting
through a file manager. Picking an outside file stays available.

### 2.6 Optional add-on — the envelope (normally A4.2)

Not required for restore to work, and easy to drop from this plan.

Today's envelope derives the key with **a fixed salt** (`List.generate(16, (i) => i)` in
`backup_service.dart`), so the same password gives the same key on every device and every backup —
exactly what a precomputed-table attack wants. Both `SreerajP_Authenticator` (`v3:` with a random
salt) and `SreerajPContactSphere` (magic + version byte + random salt) already avoid this.

Since this plan is already building "read the old format, write the new one", adding a v2
envelope with a random salt costs very little here and turns A4.2 into a documentation change.
**I recommend including it**, but say the word and it stays out and A4.1 ships against the
existing envelope untouched.

## 5. Risks

- **A restore that half-finishes.** Handled by the single transaction plus the pre-restore safety
  backup. Attachment *files* are written outside the transaction, so the restore deletes the files
  it wrote if the transaction rolls back.
- **A merge creating duplicates.** The match rules are heuristics — two entries written in the
  same second with the same title in the same journal collapse into one. The dry run exists so the
  user sees the counts first. Replace has no such risk.
- **A weaker attachment secret.** §2.4 moves attachment content from "Keystore-protected" to
  "backup-password-protected" *inside the archive file*. On the device nothing changes. This is
  the same trade `SreerajPContactSphere` makes, and it is the price of a backup that works on a
  new phone.
- **Large archives.** Restore holds the decrypted archive in memory, as verify does today.
  Acceptable for a phone-sized journal; noted, not solved here.
