# A2.1 (revised) — Tag colours

**Status:** completed

## Decisions already made

Taken from the discussion that produced this plan:

- Tags stay **global**. One shared `Tags` table for the whole vault. No per-journal tag rows.
- Tags are **for journals**. Entry tags stay exactly as they are today — no removal, no
  migration, no change to the backup format.
- **No limit** on how many tags a journal may have. No cap, no warning.
- **Nested tag paths (`work/projects/vault`) are dropped.** Journals already provide the
  grouping, so the tag tree is not needed.

So A2.1 shrinks to one thing: give tags a colour, and show that colour wherever a tag appears.

## What the issue is

1. `Tags` has no colour column. Every tag chip on the journal card is drawn in
   `scheme.primary`, so 200 tags all look identical — see `lib/app/app.dart` lines 1371-1386.
2. There is **no way to manage tags after they are created.** The tags field in the journal
   form is wrapped in `if (!isEdit)` (`lib/app/app.dart` line 1485), so tags can only be typed
   once, when the journal is created. `_openForm` accepts `initialTags` and the edit branch
   (lines 1069-1078) never reads `result.tags`. Editing a journal silently ignores tags. This
   is not data loss — existing tags are kept — but it means a colour picker has nowhere to
   live today.

Point 2 has to be solved for point 1 to be usable.

## Plan for the fix

### 1. Schema — add the colour column

- `lib/core/database/app_database.dart`
  - Add `IntColumn get colorArgb => integer().nullable()();` to `Tags`.
  - Bump `schemaVersion` from 7 to 8.
  - Add a `if (from < 8)` branch to `onUpgrade` calling
    `m.addColumn(tags, tags.colorArgb)`. Nullable, so existing rows need no backfill.
- Regenerate `app_database.g.dart` with `dart run build_runner build --delete-conflicting-outputs`.

`null` means "no colour chosen". It is not the same as a colour, so the UI needs a fallback —
see step 2.

### 2. Colour resolution

New file `lib/features/tags/domain/tag_colors.dart`:

- A fixed palette of about 12 colours that work in both light and dark themes.
- `Color colorForTag(Tag tag, ColorScheme scheme)` — returns the stored `colorArgb` when set,
  otherwise a palette entry picked by a stable hash of `tag.name`.

The hash fallback means all existing tags get distinct colours immediately, with no migration
and no user action. Picking a colour by hand just overrides it.

### 3. Tag manager

New file `lib/features/tags/presentation/tag_manager_screen.dart`:

- Lists every tag from `tagsDao.getAllTags()`, each with its colour swatch and name.
- Tap a tag → rename it, or pick a colour from the palette, or clear the colour back to auto.
- Delete a tag (removes its `journal_tags` and `entry_tags` rows first — neither FK cascades
  from the tag side today, so this must be explicit).
- Reached from the Home screen app bar in `lib/app/app.dart`.

New DAO methods in `TagsDao`:

- `setTagColor(int id, int? colorArgb)`
- `renameTag(int id, String name)` — reuse `updateTagById`, no new method needed if it is
  enough.
- `deleteTagWithLinks(int id)` — deletes `journal_tags` and `entry_tags` rows, then the tag.

### 4. Fix journal tag editing

In `lib/app/app.dart`:

- Remove the `if (!isEdit)` wrapper from the tags field only. The lock switch and password
  fields stay create-only — changing a journal password is a separate flow and out of scope
  here.
- In the edit branch of `_openForm`, apply the tags the same way the create branch does:
  read the current journal tags, work out which names were added and which removed, then call
  `addTagToJournal` / `removeTagFromJournal` for the difference.

### 5. Show the colour

- `lib/app/app.dart` lines 1371-1386 — draw each journal-card tag with `colorForTag(...)`
  instead of `scheme.primary`.
- `lib/features/smart_tags/presentation/smart_tag_chip_bar.dart` — colour the suggestion chips
  the same way, so a tag looks the same everywhere it appears.

### 6. Backup and export

- `lib/features/backup/services/backup_service.dart` lines 182-237 — `tags` is serialised from
  the row, so `colorArgb` is carried automatically once the column exists. Confirm the restore
  path tolerates the field being absent in an older backup.
- `lib/features/export/services/export_collector.dart` exports tag **names** only. Leave it —
  colour is a display concern and does not belong in an export.

## Out of scope

- Nested tag paths and the tag tree.
- Any per-journal tag limit.
- Removing or hiding entry tags.
- Filtering journals by tag colour.

## Risks

- **Schema bump.** v7 → v8 is a single nullable `addColumn`, the lowest-risk migration shape.
  The existing v1 → v7 migration test gives a pattern to copy.
- **Tag deletion.** Neither `journal_tags` nor `entry_tags` cascades from the tag side, so a
  bare `deleteTagById` would leave orphan rows pointing at a missing tag. `deleteTagWithLinks`
  must clear both link tables first, inside a transaction.
- **`lib/app/app.dart` is large.** The journal list, form dialog and detail screen all live in
  it. Changes there should stay narrow and not turn into a refactor.
