## What changed, in one line

The app can now read a backup back in. Before this, `BackupService` could write an archive and
check that it decrypted, and nothing anywhere could restore one.

## What the user sees

**Settings → Backup Health → Restore from backup.** The screen asks for the app PIN, or the
device fingerprint or screen lock when no PIN is set. Then it lists the backups the app has made,
or lets the user pick a file from anywhere on the phone, asks for that backup's password, and
shows what is inside it — when it was made, how many journals, entries and attachments, and how
large it is. The user then chooses:

- **Merge** — add what is missing, keep everything already here. Nothing is deleted.
- **Replace** — delete what is here and use the backup instead. A safety backup of the current
  data is taken first, automatically.

**Try it first** runs the whole thing without writing anything and reports what would change. The
finished restore ends with a dialog saying how much was added, how much was already there, and
how many attachment files came back.

## Three problems found while building it

None of these were in the plan as written. All three were fixed in the same pass, because each
one meant a "successful" restore would have quietly lost data.

1. **Entry moods and saved search presets were never exported.** They are user data that cannot
   be recreated. Format version 2 exports both.
2. **Attachment files went into the archive still encrypted with the device key**, which is not
   in the archive. On a replaced phone the files came back as unreadable rubble — in exactly the
   case a backup exists for. Now the files are decrypted on the way out and encrypted again with
   the receiving device's key on the way in.
3. **The archive key came from a fixed salt**, so one password produced one key on every device
   and in every backup. Version 2 uses a random salt in a self-describing header.

Voice-note files were also never written into the archive. They now are, on the same path as
attachments.

## Format version 2

`manifest.json` now carries `formatVersion`, `schemaVersion` and per-table counts. The old
`version: 1` field is still written, so an older build still recognises the file.

**Version 1 archives still restore.** Both the old envelope and the old file naming are read.
Their attachments are copied back byte for byte and keep their original nonce and key reference,
and the result dialog says plainly that those files only open on the device that made them.

Envelope layout, version 2:

```
['J','V','B'][formatVersion][kdfId][memoryKib:4][iterations][parallelism]
[saltLen][salt][nonceLen][nonce][mac:16][ciphertext]
```

The KDF settings travel in the file, so raising them later cannot orphan today's backups. A
version 1 file starts with a nonce length, never with `J`, so the two can never be confused.

## The safety sequence

In the order it runs: password (at least 8 characters) → decrypt → format version check → schema
version check, refusing anything newer with `BackupVersionTooNewException` → structure check →
plan against the current data → optional dry run, which stops here → automatic pre-restore backup
before a replace → **one database transaction** → search index rebuild → `PRAGMA integrity_check`.

Attachment files are written before the transaction, because file writes cannot be rolled back by
the database; if the transaction fails, every file written by that restore is deleted again. A
replace also deletes the files belonging to the rows it dropped, but only after the transaction
has committed.

Primary keys from the archive are **dropped, not reused**. Every row is inserted without an id and
the new id is captured, then foreign keys are rewritten from an old-to-new map. This is what stops
a merge from attaching an imported entry to an unrelated journal that happens to share id 1.

Merge matches by content: journals by title and creation time, tags by name, entries by journal,
title and creation time, attachments by entry, file name and creation time, moods by entry,
presets by name and query.

**No schema change and no migration.** The restore log reuses the free-text `trigger` column on
`backup_logs`, with the values `restore` and `pre_restore`. **No new package** — `file_picker`,
`archive`, `cryptography` and `local_auth` were already dependencies. **No native change** —
`MainActivity.kt` was not touched, because the Keystore key never leaves the device.

## Departures from the sister apps, and why

- **`sreerajp_todo` replaces the whole database file atomically.** That cannot support merge and
  does not fit a JSON-row archive. One transaction plus the automatic pre-restore backup gives the
  same "never half-applied" promise. Its WAL checkpoint before export does not apply either: this
  app exports by running queries, not by copying the file.
- **Its exception shapes were copied exactly** — `BackupVersionTooNewException`,
  `BackupCorruptedException` and the detail codes `wrong_passphrase`, `invalid_archive`,
  `integrity_check_failed` — so both apps report the same failures by the same names.
- **The dry run is new.** None of the four sister apps has one.
